## 0 · Executive summary

**The code is the strong part of this project. The market is the weak part.**

Technically, Watch Party is in unusually good shape for a ~7,700-line app built in
14 active working days: the audit found **zero Critical issues**, the sync engine was
assessed as "genuinely sound architecture," authorization is consistent across the API
surface, and the worst finding — a committed database password — is a process slip,
not a design flaw. The engineering process (phase journals, review gates, two-device
live verification) is more disciplined than most professional teams manage.

Strategically, the picture is harder. Independent research shows the watch-together
category is **post-peak and consolidated**: every first-party feature (Amazon, Disney+,
Sling) was shut down in 2023–24 for cost-vs-usage reasons; Discord gives away exactly
this product's core bundle (synced YouTube + chat + voice) for free; and Teleparty —
the only consumer survivor that charges money — already sells almost exactly this
project's planned Phase 6/7 roadmap. Worse, **YouTube's developer policies as written
prohibit overlays in front of the embedded player** (this product's floating reactions,
spotlight, and fullscreen chat overlay), constrain ads on embed-centered pages (the
Phase 6 ad plan), and ban charging to watch embedded content (fences in the premium
plan). None of this matters at friends-and-family scale — enforcement history shows
Google acts against scale + monetization — but it means **Phase 6 as currently sketched
should not be built without a redesign.**

The honest net: this is a high-quality build of a product whose realistic ceiling is a
beloved niche tool, entering a market that has structurally rejected its planned
business model. The good news is that the project's *velocity* and *quality bar* are
real assets, the beta is essentially reachable now, and there are Phase 6 shapes that
avoid the worst risks. Recommendations in §6.

## 1 · Technical assessment

### 1.1 Architecture — sound, with one honest asterisk

The three-service topology (Vercel web/API · Railway socket relay · Supabase Postgres,
LiveKit for voice) is correct for the constraints and cheap to run. Boundaries are
clean: REST for CRUD, socket for ephemeral real-time, DB as source of truth, in-memory
caches that self-heal. The decision record in the journals is excellent — nearly every
non-obvious choice (JWT session strategy for cross-service auth, client-side auto-join
to defeat link prefetch, one-fixed-DOM to protect the iframe/voice singletons) has a
written *why* that survived contact with production.

The asterisk: **`RoomShell.tsx` (976 lines) is the app's most safety-critical client
code and its least testable.** It owns both the playback-sync state machine and all
layout/view-mode logic. Every future room feature churns the same file. The audit ranks
extracting a `usePlaybackSync` hook as a pre-requisite for the next room feature —
agreed, and deferred with that framing.

### 1.2 Sync engine — validated; limits are known and acceptable

The audit's strongest praise landed here, and it matches my own read: server-stamped
state + per-client skew projection + drift tolerance + CUED-event drain + epoch-gated
reconnect reconcile is the right design for YouTube-iframe sync, and the 5.1 reconnect
work fixed the one real field failure ("refresh fixes it"). Known limits, all
consciously accepted and documented: single-host authority (host dies → room
coasts), in-memory room state (all-disconnect blip wipes position until the next
heartbeat), 2.5 s drift tolerance, and the deferred watchdog/diagnostics layer.
One product-level limit nobody has written down before: **YouTube mid-roll ads fire
per-viewer and will desync the room** — free-tier YouTube embeds serve ads to each
client independently. There is no engineering fix; it's a property of the platform.

### 1.3 Security posture — good pattern, several real gaps (most now closed)

The uniform API pattern (`requireUser` → zod → membership/role checks → narrow
selects) held up under audit: no mass-assignment, no password/secret leakage in
responses, socket JWT pinned to alg/issuer/audience, LiveKit tokens server-issued and
room-scoped. Found and **fixed this session**: an open redirect on `/signin`; a
cross-room DB write via unscoped `markItemPlayed`; unbounded `video:state` payloads;
and the LEFT-member inconsistency (three layers disagreed on what "left" means — now:
only ACTIVE members get the room, rejoins re-clear capacity). Found and **user-gated**:
the production DB password committed to `DEFERRED.md` (since **rotated + scrubbed from
history**, 2026-07-16). Remaining Mediums are pre-monetization gates, not
today-problems — chiefly subscription-tier freshness (the session tier is set at
sign-in) and an unused auth code path to remove. Specific reproduction detail for the
open items is tracked privately (`SECURITY_NOTES.local.md`), not in this public report.

### 1.4 Test depth & CI — the numbers overstate the coverage

33 tests, all green, all *pure logic* (validators, rate limiter, spotlight detector,
room helpers). Zero coverage of the authorization gates, API routes, or socket
handlers — the places where this app's actual risk lives. Until today CI didn't run
the tests or the build at all (lint + typecheck only) while every push deployed
production twice. **Fixed this session:** CI now runs the suite and a production
build. Still true: no integration/E2E tests, and the standing substitute — the
two-device live verify ritual — is honest and effective but doesn't scale beyond one
person's patience.

### 1.5 Operational maturity — the weakest technical dimension

Deploy-on-push to prod on two services · no staging · no error tracking · no uptime
monitoring · no analytics · diagnostics = `console.log` on Railway plus whatever
Vercel retains. The cost is already visible: **Known issue #5 (mobile first-attempt
sign-in failure) is undiagnosable today** because nobody can see production errors;
the fix path is blocked on a `VERCEL_TOKEN` that only you can create. This posture was
a reasonable trade for a friends-and-family app. It stops being reasonable the day
Stripe webhooks or public users arrive. Sentry (or similar) on both services is hours
of work and is the highest-leverage ops improvement available.

## 2 · Product assessment

### 2.1 What's genuinely good

The invite loop (link = room URL, auto-join, prefetch-safe) is one-tap and correct.
The room itself — view modes, mobile tabs, combined People panel, reactions,
catch-up modal — is coherent and polished, and friend-test feedback visibly shaped it
(5.1 reliability, the People-panel merge, controls moved off the video). The PWA is
conservative and sane. This is a real product, not a demo.

### 2.2 The friction list, ranked by first-impression damage

1. **Issue #5 — mobile Google sign-in fails on first attempt** (works on retry).
   Sign-in is the first thing every invited friend does, on the device they were
   invited on. A red "Sign-in failed" box is the single worst possible first
   impression, and it's currently a mystery. *Status: blocked on the error code or
   Vercel logs; auth deliberately untouched per spec.*
2. **B2 — voice doesn't work on mobile Safari** (`NotAllowedError`, open since
   June 17). Voice is a headline feature; iPhones are half the invite pool.
3. **`/signup` is a live stub** ("Sign up — coming in Step 1.5") and `/signin` says
   "Email & password sign-in coming soon." Anyone without/unwilling to use a Google
   account is turned away at the door, and the stub reads as abandonment.
4. **Rooms never end.** No close-room, no auto-expiry; every room ever created sits
   on the dashboard forever and holds its members. Clutter today, capacity/moderation
   problem later. (Audit Medium; the leave route even references a close action that
   doesn't exist.)
5. **Viewer join UX asterisk:** viewers start muted (autoplay policy — correct) with
   a text hint to unmute. Acceptable; a first-class "tap to join with sound" overlay
   is the polished version.

### 2.3 Retention — the honest gap

Nothing brings a user back. No history ("you watched 7 things with Sarah"), no
scheduling/RSVP, no recurring rooms, no watchlists, no notifications. Phase 9 knows
this — but as sequenced (after monetization, cross-platform, moderation) the product
spends months monetizing and porting a thing that has no reason to be reopened next
Friday. The category graveyard says retention-after-novelty is kill-pattern #3.
**Recommendation in §6: pull one Phase 9 coordination feature ahead of Phase 6/7.**

### 2.4 Completeness vs. the Phase 6 sketch

Phase 6 assumes: Stripe premium tiers, AdSense, affiliate links, premium themes.
Against reality: the tier system exists in schema but the JWT freezes it; themes have
an engine but no premium rendering; ad slots exist as schema models only; **and the
whole ad half collides with YouTube policy** (§3.2). Phase 6 is not "wire up Stripe" —
it's a strategy decision that hasn't been made yet.

## 3 · Viability assessment

### 3.1 Scalability ceilings (engineering)

Fine for hundreds of concurrent users, in order of first-to-bite:

- **LiveKit Cloud free tier** — 100 concurrent participants / 5 GB — voice is the
  first hard wall if usage grows.
- **Single Railway socket node** — no horizontal path (in-memory rooms preclude it
  without a Redis adapter), but a lightweight relay handles low thousands of sockets;
  not a real near-term constraint.
- **Supabase Session pooler** — serverless functions + pooler is workable;
  unbounded `Message`/`Reaction` growth (no retention job despite the 48 h promise)
  is the actual DB risk.
- **YouTube Data API quota** — amusingly, zero: the key is configured but never
  called (titles are client-supplied, `durationSecs` never fetched).

None of these are launch blockers. All are known, cheap-ish, and boring — which is
the correct kind of scalability problem to have.

### 3.2 Platform risk — the serious one

From the researched YouTube API Services policies (primary sources, opened):

- **"API Clients must not… place overlays… in front of any part of a YouTube
  embedded player."** The floating reactions, spotlight reactions, and fullscreen
  chat overlay — the product's signature delight layer — violate this as written.
- **Ads require non-YouTube content on the page** and can't be sold against the
  embed as the centerpiece → the Phase 6 AdSense plan is squarely gray-to-violating.
- **"Must not charge users to watch content in an embedded player"** → premium must
  fence *social* features (room size, cosmetics, voice), never playback.
- **Enforcement precedent is real** (Groovy/Rythm Discord bots, 16 M servers, killed
  2021) and triggers on **scale + monetization** — friends-and-family use is
  practically invisible, but the risk curve rises exactly when the product starts to
  succeed. That's the definition of a structural risk.

### 3.3 Competitive context (researched, cited in the brief)

- **Discord** ships synced YouTube + chat + voice, free, inside the app your target
  users already have open. That's the default alternative to beat, and "we're a
  focused, cozier theater" is the only available differentiation.
- **Teleparty** (20 M+ self-reported users) owns the premium-extension lane this
  project's Phase 7 targets: Netflix/Disney+/Prime sync free, voice/video and
  cosmetics behind a $6.59/mo premium. Phase 6+7 as planned re-builds Teleparty's
  existing product, from zero distribution.
- **The graveyard** (Rabbit, Kast, Squad, Rave, plus Amazon/Disney/Sling first-party)
  died of: rights-encumbered ad models, per-user infra costs, post-novelty retention
  collapse, and platform gatekeepers. This project's plan intersects all four; its
  YouTube-embed + tiny-infra design at least keeps the cost pattern mild.
- **No watch-together product has demonstrably sustained itself on ads.** Rabbit
  tried; advertisers refused to buy against content it didn't own. Drop the ad plan.

### 3.4 Legal/compliance gaps for anything public

No ToS, no privacy policy, no account deletion, no data-export path — while storing
emails, OAuth identities, chat logs, and (post-Phase-6) payment linkage. GDPR/CCPA
exposure starts the day a stranger signs up. Moderation (Phase 8) is sequenced
*after* monetization; for a product with rooms + chat + voice, public launch without
report/kick/ban is not viable — reorder it.

## 4 · Outlook — timeline and projections

### 4.1 Velocity, from git history

14 active working days across 46 calendar days (May 26 → Jul 10), bursty: a 4-day
sprint built Phases 1–4.3; deployment took 3 sessions; the entire Phase 5 series took
~6 active days. Sustained cadence ≈ **2 active days/week**, with a demonstrated
"phase" (feature + review + verify + docs) costing **1–2 active days**. These numbers
are unusually reliable — the journals timestamp everything.

### 4.2 Timeline to milestones (at current cadence)

**(a) Friends-and-family beta — ready in ~2–4 weeks (3–5 active days).**
The app is already live and friend-tested; what "beta" honestly still needs:
5.6 live verify (user-gated) · DB password rotation (user, 15 min) · issue #5
diagnosed and fixed (1 session with logs) · B2 mobile-Safari voice fix (1 session) ·
error tracking installed (half a session) · close-room shipped (half a session).

**(b) Public-launch-ready — ~3–5 months (25–40 active days), if scope is decided.**
Adds, roughly in cost order: moderation minimum — report/kick/ban/close (3–4 d) ·
Stripe premium + tier-refresh design + webhook hardening + staging (4–6 d) ·
ToS/privacy/account-deletion (2–3 d) · retention crons + rate-limit hardening +
capacity race (2 d) · monitoring/alerting + load test (2–3 d) · onboarding polish:
signup story, guest access decision, viewer-unmute UX (3–5 d) · `usePlaybackSync`
extraction + auth-gate tests (3–4 d) · buffer for the unknowns a first public cohort
always surfaces (≥ 5 d). **Not included:** the Chrome extension or native apps
(Phase 7) — both are new products, not launch requirements, and §6 argues against
the extension entirely.

### 4.3 Projections

- **Best case (achievable, not probable):** the cozy-theater positioning + invite
  loop finds its niche — long-distance couples, D&D groups, anime clubs. Low
  thousands of MAU by word-of-mouth; premium (rooms/cosmetics/voice, ~$4–6/mo)
  converts 2–4% and covers infra with beer money left; the product stays deliberately
  small and YouTube-compliant, below enforcement altitude. This is the realistic
  ceiling: **a sustainable, loved, niche tool — Kosmi-sized, not Teleparty-sized.**
- **Likely case:** a polished product used regularly by its builder's extended circle
  and sporadically beyond; growth stalls against "we already do this in Discord";
  monetization never justifies its build cost; the repo remains a first-rate
  portfolio piece and the friend group keeps its movie nights. That is not failure,
  but it should be chosen consciously, not drifted into.
- **Kill risks, ranked:** (1) YouTube ToS enforcement the moment ads/overlays meet
  scale — structural, mitigable only by redesign; (2) retention cliff — the graveyard's
  common cause; (3) Discord/Teleparty incumbency suffocating the top of funnel;
  (4) solo-maintainer bus factor + ops blindness during a paid-user incident;
  (5) moderation/abuse liability if public launch precedes Phase 8.

## 6 · Recommended Phase 6/7 shape

**Drop:** the entire ad stream (category-proven failure + ToS collision + premium is
the better wedge anyway). The affiliate idea can stay as a dormant hook.

**Reshape Phase 6 into "trustworthy + retained + modestly premium":**
1. **Compliance pass first** — move reactions/spotlight/chat-overlay *off* the player
  surface (beside/around the stage, not over it). This hurts; the overlay is charming.
  But it converts the #1 structural risk into a styling constraint, and it must happen
  before the product is worth money. Get the premium fence reviewed against the
  "charge to watch" clause (fence voice/cosmetics/room-size — never playback).
2. **One retention feature pulled from Phase 9** — recurring rooms ("Friday Movie
  Night") or schedule+RSVP. Cheapest counter to the category's #1 killer.
3. **Moderation minimum + lifecycle** (close-room, kick/ban, report) — pulled forward
  from Phase 8; also unblocks the dead schema paths the audit flagged.
4. **Stripe premium** — small: bigger rooms, themes, persistent rooms — after the
  tier-refresh design and behind a staging checkpoint.

**Phase 7 rethink:** the Chrome extension is a head-on assault on Teleparty's core
free product with zero distribution advantage — cut it or demote it to
curiosity-shelf. Native apps remain premature until retention exists. The PWA is the
mobile strategy and it already works.

## 7 · Session record — what the fix pass changed

Applied under ritual Part A (build → review-logic on the diff → apply its findings →
unit-test new pure logic → tests/typecheck/lint/build → push):
- `/signin` open redirect closed. First cut (prefix check) was **caught by
  review-logic as bypassable** (`/\evil.com` — browsers treat `\` as `/`; plus a
  crash on repeated query params). Final fix: `lib/callback-url.ts`
  `sanitizeCallbackUrl` — WHATWG URL-parse against a sentinel origin — with 9 unit
  tests covering the bypass classes (backslash, protocol-relative, tab-injection,
  absolute, string[]).
- Socket: `room:join` now requires ACTIVE; `markItemPlayed` scoped to the room;
  `video:state` payload bounded (finite position ≤ 48 h, itemId ≤ 64 chars).
- LEFT-member invariant closed across every layer: room page routes LEFT/KICKED
  through JoinGate; REST join re-runs the capacity gate for any non-ACTIVE joiner;
  queue GET/DELETE now require ACTIVE (review-logic caught these two REST holes).
- CI: tests + production build now gate every push (verified against placeholder env).
- `DEFERRED.md`: password scrubbed (rotation pending, user-gated), 2026-07-10 audit
  backlog recorded with rationales, 2026-06-27 socket list marked superseded.
- Auth (`lib/auth.ts`) deliberately untouched — issue #5 diagnosis first.
- Final state: **42 tests · typecheck · lint · build all green.**
